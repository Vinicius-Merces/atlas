# Design System Contribution Workflow

## Trigger

A new token, component, variant, pattern, or breaking design-system change is
proposed.

## Sequence

1. Confirm recurring need.
2. Search existing tokens and components.
3. Define semantic purpose.
4. Design API, states, and accessibility.
5. Implement and document examples.
6. Validate themes and responsive behavior.
7. Review migration impact.
8. Version and release the contribution.

## Blocking conditions

- Product-specific logic in a shared primitive
- Missing accessibility states
- Undefined migration for breaking change
- Duplicate component without justification
