# Lead Mutation Contract — Visit Request

Capability: `form-mutation-design` (+ `rate-limit-abuse-control`, `conversion-funnel-review`,
`analytics-implementation-audit`)
Workflow: `site-from-brief-delivery` (steps 5, 8, 9)

## 1. Authoritative mutation

| | |
| --- | --- |
| Actor | Anonymous public visitor |
| Resource | `visit_request` row in the server-side SQLite database (`data/asteria.db`) |
| Endpoint | `POST /api/visit-requests` (Node runtime, same origin) |
| Precondition | Payload passes server-side schema; rate limit not exceeded; honeypot empty; `residenceId` (when given) resolves to a real residence |
| Invariant | One accepted request per `(idempotency_key)` and one per `(email, residence_id, day_bucket)` — enforced by two `UNIQUE` indexes inside a single transaction, not by application-level "check then insert" |
| Resulting state | `visit_request` row with server-generated `reference` (`AST-` + 8 crockford base32 chars), `status='received'`, `notification_status ∈ {pending, delivered, failed}`, `created_at` |
| Authoritative proof | `GET /api/visit-requests/:reference` with header `x-asteria-admin-key` returns the stored row. Used in evidence to prove the lead exists **server-side**, independent of any UI toast. |

### State transition map

```
(none) --POST valid--> received/notification:pending
                          |--broker notify ok----> received/notification:delivered
                          |--broker notify fail--> received/notification:failed  (retryable, NOT lost)
(none) --POST invalid--> (none)            422 + field errors
(none) --POST duplicate--> existing row     200 + same reference + duplicate:true
(none) --POST over limit--> (none)          429 + retry-after
(none) --POST store fail--> (none)          503 + explicit "not received" copy
```

The lead is persisted **before** the broker notification is attempted. A broker/provider failure
therefore can never lose a lead; it degrades to `notification_status='failed'` with the reference
still issued and a visible, honest message telling the visitor the request *was* recorded and giving
them the phone number as a second path. This is the fixture's "a client-side success toast is not
proof" requirement inverted into the design.

## 2. Client vs server validation

Client validation is **convenience only** and is duplicated, never trusted:

| Field | Server rule |
| --- | --- |
| `name` | 2–80 chars after trim |
| `email` | RFC-shaped, ≤ 254, normalised to lower case |
| `phone` | optional, 6–24 chars, digits/`+`/space/`-`/`(` `)` |
| `residenceId` | optional, must match `^A(0[1-9]\|1[0-2])$` **and** exist in content |
| `timeframe` | enum `immediate` \| `3-6-months` \| `6-12-months` \| `exploring` |
| `context` | enum `primary-home` \| `second-home` \| `investment` \| `broker` |
| `preferredDates` | optional, ≤ 120 chars |
| `message` | optional, ≤ 2000 chars |
| `consent` | must be exactly `true` (explicit contact consent; recorded with timestamp) |
| `website` | honeypot — must be empty; non-empty is accepted with a 200 and silently discarded |
| `idempotencyKey` | UUID v4 shape; generated by the client per form instance, regenerated after a successful submit |

Error shape (stable contract):

```json
{ "ok": false, "error": "validation_failed",
  "fields": { "email": "Enter a valid email address." },
  "message": "Some details need attention." }
```

Field errors are rendered inline, associated with `aria-describedby`, the field gets
`aria-invalid="true"`, the error summary is a focusable region announced via `role="alert"`, and
focus moves to the first invalid control. No error is communicated by colour alone.

## 3. Concurrency and idempotency

- `idempotency_key` carries a `UNIQUE` index. A repeated POST with the same key returns **200 with
  the original reference and `duplicate: true`** — never a second row, never a 500.
- A second `UNIQUE` index on `(email, residence_id, day_bucket)` stops a determined double-submit
  from a fresh key creating two leads for the same person and residence on the same day.
- Both inserts run inside `BEGIN IMMEDIATE`, so two concurrent identical requests resolve to one row
  plus one duplicate response. Exercised with parallel requests in the evidence.
- The submit control is `disabled` with `aria-busy` while pending, but that is UX, not the guarantee.

## 4. Abuse control

- Token bucket per client IP: 5 accepted requests / 10 minutes, `429` with `Retry-After` beyond that.
- Honeypot field, visually hidden, `tabindex="-1"`, `autocomplete="off"`.
- Minimum time-to-submit: a form rendered and submitted in under 2s is treated as automated and
  answered `429`.
- Payload cap 16 KB; `Content-Type` restricted to `application/json` and
  `application/x-www-form-urlencoded`.
- No secret ever reaches the client: the broker webhook URL and the admin key live only in server
  env (`ASTERIA_BROKER_WEBHOOK`, `ASTERIA_ADMIN_KEY`) and are asserted absent from the client bundle
  in evidence.

## 5. UI states (all implemented, all evidenced)

| State | Behaviour |
| --- | --- |
| Idle | Form with a stated purpose, response-time promise, and privacy link |
| Pending | Submit disabled, `aria-busy`, status region announces "Sending your request…" |
| Success | Server-issued reference shown verbatim with what happens next and by when. No confetti, no vague "we'll be in touch". |
| Success with degraded notification | Same reference, plus an honest notice that the broker hand-off is retrying and a direct phone number |
| Validation error | Inline errors + summary + focus management |
| Duplicate | "We already have this request" + the original reference + no second row created |
| Rate limited | Explicit wait time + phone fallback |
| Server/store failure | Explicit **"your request was not received"**, the entered values preserved, a retry control, and the phone number. Never a success shape. |
| Offline / ambiguous network | `fetch` rejection is treated as *unknown*, not failure: the copy tells the visitor the request may or may not have been received and gives them the reference-check path, and the same idempotency key is reused on retry so a retry cannot duplicate. |
| No JavaScript | Native form POST → server-rendered confirmation page carrying the same reference |

## 6. Conversion analytics

First-party and server-side. `conversion.visit_request.submitted` is recorded **in the same
transaction as the lead insert**, keyed by `reference`, so it is structurally impossible to emit a
conversion event for a lead that does not exist or to emit two events for one lead. Funnel steps
(`residence_detail_viewed`, `enquire_opened`) are recorded via a small `sendBeacon` call to
`/api/events` with a per-session id and a server-side dedupe window. No third-party analytics script,
no client-side "success" event. Verified in evidence by comparing event counts to row counts.

## 7. Negative-path evidence plan

1. Empty submit → 422 + inline errors + focus on first error (browser).
2. Malformed email + missing consent → field-level errors (browser).
3. Valid submit → 200 + reference; then authenticated read-back proves the row (browser + API).
4. Same idempotency key replay → 200, `duplicate:true`, row count unchanged (API).
5. Two parallel identical POSTs → exactly one row (API).
6. Broker webhook forced to fail (`ASTERIA_BROKER_MODE=fail`) → lead still stored,
   `notification_status='failed'`, degraded success UI (browser + API).
7. Store forced to fail (`ASTERIA_STORE_MODE=fail`) → 503, explicit "not received" UI, no row
   (browser + API).
8. Rate limit exceeded → 429 + wait-time UI (API + browser).
9. JS disabled → native POST confirmation page with reference (browser).
10. Bundle secret scan → no `ASTERIA_ADMIN_KEY` / webhook URL in any client asset.

## 8. Residual risks

- SQLite on a single node is appropriate for this volume but is not multi-region; recorded as a
  known scaling boundary, not hidden.
- The broker webhook retry is in-process with bounded attempts; a durable queue is the documented
  next step if lead volume or the broker SLA changes.
- Email delivery to the visitor is out of scope in this environment (no reachable mail provider);
  the confirmation is on-page and by reference code, and this limitation is stated in the run notes
  rather than simulated.
